# KTB Health monorepo — agent guide

## Org repos — use them, don't reinvent

Sibling clones live next to this repo (`../<name>`); canonical sources
on GitHub under `github.com/ktbhealth/`. This repo is
`github.com/ktbhealth/product` (renamed from `ktbhealth/ktbhealth` —
old URLs redirect).

- **`ui`** (`@ktbhealth/ui`) — THE design system: Tailwind v4 tokens +
  React (`@react`) and Vue component libraries. Source of truth for all
  UI. Consumed via git-tag deps (`github:ktbhealth/ui#vX.Y.Z@react`).
  - Never copy/vendor components into apps — missing component? Add it
    in `ui`, tag a release (`git tag vX.Y.Z`), bump the dep here.
  - Never edit `node_modules/@ktbhealth/ui` — changes are lost.
  - Same rule for `slidev-theme-ktb` (deck theme) and any other
    `github:ktbhealth/*` dep: fix upstream, tag/commit, bump the dep.
- **`storybook`** — component catalog for `ui`. Before building any UI,
  check existing stories/usage (`bun run dev` → :3100). New components
  get stories there.
- **`project`** — myco ledger: proposals, ADRs, tasks across all org
  repos. Rules: `../project/AGENTS.md`. The loop:
  `myco status --prompt` at session start → track work with
  `myco todo add` / `proposal new` → `myco item set <ID> --status …`
  as you go → `myco handoff <ID>` when wrapping up. Never hand-edit
  `project/` files — myco verbs are the write path.
- **`presentation-draft`**, **`website-draft`**, **`slidev-theme-ktb`** —
  pitch/site/theme repos; not part of this build.
- **`docs`** — documentation site (Fumadocs + TanStack Start on
  Cloudflare Workers); product/architecture docs live there, not here.

## Commands

- `bun run check` — fmt + lint + typecheck (run before committing)
- `bun run test` — vitest per-package
- `bun run build` — production build (root builds apps/web)
- `bun run gen:route-types` — regenerate `plugins/*/src/route-types.d.ts`
  (generated; never hand-edit) after route changes
- `cd apps/web && bun run infra:deploy` — deploy to Cloudflare prod
  (needs cuora vault access)

## Conventions

- English everywhere (code, comments, commit messages).
- Domain logic as Effect services behind ports; adapters at the edge
  (see ADR-0001 in project repo — transcription sources, and the
  calendar/notification ports in P-008/P-009).
- Arch lint: plugins must not import from apps — inject via route
  composition (`api` objects in `apps/web/src/routes/`). Boundary
  policy lives in `tools/arch-policy.mjs` (single source for the oxlint
  overrides + `ktb-arch/*` rules): ports/plugins may not import adapters,
  use `node:*`/`bun:*`/`deno:*`/`cloudflare:*`/`workerd:*`, touch
  `process`/`Bun`/`Deno`, or hardcode provider literals (`@cf/*`
  model ids, provider endpoints). Adapters, apps/_, infra/_ and
  @ktb/app-host are the exempt edge; tests keep adapter-import bans but
  are exempt from platform/provider rules.
- packages/ vs plugins/: `plugins/` = registry citizens — they
  contribute tables/services/routes/nav/chrome/pages/panel AND can add
  capabilities other plugins consume (services, CQRS groups, events)
  with `requiredDeps`/`optionalDeps` ordering (see patients.services →
  consultations). Plugin ids follow `<domain>.<concern>`
  (`patients.services`, `platform.routes`) and deps always target those
  concern-level ids — never package names. `packages/` = infra BELOW the plugin system: ports,
  adapters, drivers, env composition (db, authz, tenant, bot, captcha)
  that plugins consume but that never join the registry. Rule of thumb:
  needs registry contributions or plugin-graph deps → `plugins/`;
  reusable infra → `packages/`. A package may get a thin `plugins/`
  wrapper when it needs registry contributions (see `packages/rbac` vs
  `plugins/rbac`). `packages/platform` (`@ktb/platform`) is host
  infrastructure (admin gate, console shell, plugin_state) that lives
  below the plugin system but still contributes registry entries —
  `@ktb/app-host` registers its `plugins` manifests explicitly next to
  the `plugins/*` filesystem glob (T-088).
- Apps are composition roots: `apps/web/src/lib/` holds only
  app-bound wiring (i18n, server fns, runtime registration, deploy
  adapters). Generic logic belongs in packages — currently
  `chrome`/`pages`/`plugin-state` collection is being extracted to
  `@ktb/app-host/client` (T-086).
- Positioning: documentation-only — the physician decides, KTB
  records. No diagnosis/treatment/recommendation copy (T-021).
- Server fns validate wire input with effect/Schema — tolerate
  null/undefined/string coercions (see `normalizePatientId` in
  `apps/web/src/lib/fns.ts`).
- Generated files are never hand-edited: Paraglide output
  (`src/paraglide/`), `routeTree.gen.ts`, drizzle migrations are
  regenerated by the toolchain (`vp build`/`check`, `db:generate`).
- Tests: the repo-wide vitest coverage gate is 100% — partial/package
  runs fail on unrelated files. Scope runs per package
  (`cd <pkg> && bunx vitest run`) and don't chase the global threshold.
